# Municipal permit and application field audit

Checked November 18, 2026 against the City of New Haven's public [Municity permit 569338](https://www.municityconnect.com/#/app/NewHavenCityCT/entity/Permit/569338/Document) and its official vendor service. The selected permit is `P-22-00708`, at `201 WEST PARK AV`; its source row lists vendor `Parcel_ID` 22232 and `PrintKey` `352 1131 01800`. The permit row names `Application_ID` 22797. This is a source relationship, not a match inferred from a shared permit number.

The parcel `Children` response already supplied the permit and application rows to the parcel API/MCP. For this example, that permit child row has 174 fields. An exact public `GetM5Data` search by `Permit_ID` returns 229 fields, including vendor flags and the explicit `Parcel_ID` absent from the parcel child row. The exact search result is accepted only when its permit ID, parcel ID, and PrintKey match the selected parcel. The new on-demand `get_permit_details` tool returns that full permit row and the exact, similarly verified linked application row. If the full search is unavailable, it labels the response partial and keeps the verified parcel child row.

| Source relationship | Official rows seen for permit 569338 | API/MCP treatment |
| --- | --- | --- |
| Permit parent | Permit number, type, status, department, dates, work and address fields, plus the complete returned field set | Full source fields returned with a direct link to the permit. The example's `Department` is `Plumbing (1 and 2 Family only) - Public` and `PermStatus` is `Issued`; these remain the City's source labels. |
| Linked application | `Application_ID` 22797 in the permit row; application 22797 also appears on the same verified vendor parcel | Exact application search and child rows are included when its parcel ID and PrintKey verify. Full source fields and direct application link are returned. |
| Fees | Two fee rows, amounts `77.52` and `30`, with category, type, paid and voided fields, invoice/payment metadata and application number | Returned as separate rows with source field names and strings preserved. `FeePaid` is source reported; no total or independent payment conclusion is invented. |
| Review tasks | One task, `Plumbing Review`, `ApprovalStatus` `Approved`, `Entity` `Application`, `Entity_ID` 22797 | Returned as a task linked to the permit and application. `TaskType`, `Subject`, `AssignedTo`, approval status and dates are retained. `AssignedTo` is a source value, not a derived department. Internal notes are omitted. |
| Documents | Four permit child rows; three marked public and one private | Only public, nondeleted metadata and verified official media links are returned. Files are not downloaded or stored. |
| Contacts and communications | Contact roles and communication metadata appear under permit and application | Role summaries and message titles/dates are returned. Phone, email, mailing address, message body and recipients are omitted. |

The permit and application child responses both contain `Communication`, `Contact`, `Document`, `Fee`, and `Task` arrays for this example. Rows with the same source category and ID are returned once with both `linked_from` relationships. Missing child categories are labeled “not returned,” and failed or truncated checks mark the detail response partial. The public endpoint did not return an inspection category for this example, so the API does not assert inspection coverage or a complete review history.

The lookup runs on request through the existing five-minute source cache. No permit database or document copy is created. The parcel Activity list remains compact; opening a permit's “Fees, reviews and related records” panel calls the protected REST endpoint. MCP clients call `get_permit_details` with the selected City parcel ID and municipal permit ID. An ID from a different parcel is rejected.
